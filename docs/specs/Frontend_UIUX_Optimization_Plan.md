# KnowPilot 前端 UI/UX 优化计划（27 项 + 2 优先级建议）

> 版本：前端优化版
> 定位：**以"功能描述 + 预期结果"为主**；由于前端改动风险可接受，本计划在已核实处给出**具体改动方向**，未核实处仅给描述与预期结果，不臆测。
> 运行方式：Docker（`config.settings.docker`）。**前端为构建镜像 + nginx 服务，任何改动须先 `git add` 再 `docker compose build frontend` 重建镜像才生效**。
> 数量说明：清单含 **27 个优化项**（工具标注 5 高 / 14 中 / 其余低）+ **2 条优先级建议** = 用户所指的 **29**。下文将 27 项按主题分为 A–G 组，各配预期结果，末尾单列 2 条建议。

## 0. 通用前提与已核实事实

- 设计令牌集中在 `frontend/src/design/tokens.ts`（亮/暗两套色），经 `theme.ts` + CSS 变量（`--color-text-secondary` 等）注入全局；**颜色类问题优先改 tokens.ts，单点生效、影响可控**。
- 已核实令牌值：亮色 `textTertiary #817A70`(L16)、`textSecondary #655E57`(L15)；暗色 `textSecondary #B5ADA3`(L44)、`textTertiary #B8B0A8`(L45)；`--color-bg-section: rgba(accentRgb, 0.025)`(L214)。
- 已核实：`--accent-bg` / `--accent-border` 在 `WorkspaceCreationPage.css`(L61/L169-170) 被使用，但 `tokens.ts` **未定义**。
- 已核实：`ForbiddenPage` 位于 `frontend/src/auth/CapabilityGate.tsx`（L14，标题仅 "Access denied"）；注册逻辑在 `frontend/src/auth/LoginPage.tsx` `handleRegister`(L129)，**注册表单已用 `validateTrigger="onBlur"`(L255)**。
- 已核实：`AdminDashboardPage.tsx` 的 `roleStyleMap`(L145)/`healthStyleMap`(L151) 使用硬编码十六进制颜色。
- 规范（强制）：新增/修改颜色一律走 CSS 变量，暗色模式默认支持，**对比度须达 WCAG AA**（正文 ≥4.5:1，边框/图形 ≥3:1）。参见项目《前端暗色模式与对比度审查规范》。
- 验证：前端改动后需重建镜像，再跑 `lint` / `typecheck` / `test` / `check:i18n` / `build`；颜色改动辅以对比度自测。

## A. 新用户认证与权限引导（高优先 · 注册→403 流失链）

### A1｜注册成功后跳转需空间权限页面导致 403 【高】
- **描述**：`LoginPage.tsx` `handleRegister` 注册成功后直接 `login({token,user})` 并跳转，但新用户尚未加入任何空间，`default_space` 可能为 null，后端返回 403。
- **预期结果**：新注册用户成功后被引导到"加入/搜索空间"页面（而非直接进受空间权限保护的页面），不再出现开局 403；无空间用户有明确的下一步入口。

### A2｜403 错误页面无可操作引导按钮 【高】
- **描述**：`CapabilityGate.tsx` `ForbiddenPage` 仅显示 "403 / Access denied"，无返回首页、查看我的空间、申请加入空间等按钮。
- **预期结果**：403 页面给出原因说明 + 至少"返回首页 / 查看我的空间 / 申请加入空间"操作按钮，用户明确知道为何被拒与如何自救。

### A3｜路由守卫未区分未认证与已认证无权限 【高】
- **描述**：`ProtectedRoute.tsx` 仅判断 `isAuthenticated` 布尔，未区分"未认证 / 已认证无空间 / 已认证有空间"三态。
- **预期结果**：路由守卫实现三态分流——未认证→登录页；已认证无空间→空间引导页；已认证有空间→正常放行；不再把"已登录无空间"误导回登录页或裸 403。

## B. 操作反馈、防误操作与表单体验（中优先）

### B1｜危险操作缺少二次确认弹窗 【中】
- **描述**：删除文档、退出空间、移除成员等不可逆操作无二次确认。
- **预期结果**：所有不可逆/高危操作均有二次确认（`Popconfirm`/`Modal.confirm`）；最高危操作要求输入名称确认，杜绝误触即执行。

### B2｜关键操作按钮缺少 loading 状态和禁用 【中】
- **描述**：注册、保存、创建空间等按钮无 `loading`/`disabled`，可重复点击导致重复提交。
- **预期结果**：关键操作按钮在请求期间显示 loading 并禁用，防重复提交，用户能感知"进行中"。

### B3｜操作成功/失败后缺少 Toast 反馈 【中】
- **描述**：注册、保存、创建、删除等关键操作缺少成功/失败反馈。
- **预期结果**：关键操作结束统一给出 Toast/Notification（成功/失败均有），用户可确认操作是否生效。

### B4｜空状态页面缺少创建入口和引导操作 【中】
- **描述**：无空间/无文档/无消息等空状态仅显示"暂无数据"。
- **预期结果**：空状态提供明确 CTA（如"创建空间/上传文档/发起对话"），用户知道下一步该做什么。

### B5｜表单校验时机与密码强度 【中】
- **描述**：清单称"表单校验仅在提交时触发"。**已核实注册表单已为 `onBlur`**，故此项聚焦其余表单的一致性与密码强度提示。
- **预期结果**：所有关键表单统一采用失焦(onBlur)/实时校验；密码字段显示强度指示器；提交前即暴露错误，减少"提交后才报错"。

### B6｜错误提示信息为技术性文案 【中】
- **描述**：错误提示为 `Permission denied`、`JWT expired` 等技术文案。
- **预期结果**：建立错误码→用户友好自然语言的映射表，界面展示可理解的中文/英文提示；技术细节仅进日志。

### B7｜数据加载期间缺少骨架屏 【中】
- **描述**：加载期无 Skeleton，内容到达后布局闪烁。
- **预期结果**：列表/卡片/详情在加载期显示 Ant Design `Skeleton` 占位，内容到达无跳变。

## C. 响应式与页面过渡

### C1｜移动端响应式适配不足 【中】
- **描述**：<768px 下表格溢出、侧边栏遮挡内容。
- **预期结果**：移动端表格转卡片、侧边栏改抽屉、多列变单列、主操作按钮固定底部；核心页面在窄屏可正常使用无溢出。

### C2｜页面跳转缺少过渡动画 【低】
- **描述**：路由切换内容突然替换，体验生硬。
- **预期结果**：用 `framer-motion` `AnimatePresence` 为路由切换加 200–300ms fade/slide 过渡，切换平滑（尊重 reduce-motion）。

## D. 设计令牌与暗色模式 WCAG 对比度（改 `tokens.ts` 单点生效）

### D1｜AdminDashboardPage 硬编码颜色无暗色适配 【中】
- **描述**：`AdminDashboardPage.tsx` L145-161 `roleStyleMap`/`healthStyleMap` 含 15+ 硬编码十六进制（全亮色值），暗色下形成刺眼亮块。
- **预期结果**：改用 CSS 变量/主题令牌驱动，暗色模式下角色/健康标签配色协调、无亮块。

### D2｜暗色 textSecondary 与 textTertiary 亮度差极小 【中】
- **描述**：暗色 `textSecondary #B5ADA3` 与 `textTertiary #B8B0A8` 亮度差仅约 0.017，三级文本层级丢失。
- **预期结果**：调暗 `textTertiary`（参考 `#988F84` 左右），二/三级文本层级肉眼可区分。

### D3｜暗色模式边框对比度低于 WCAG 【高】
- **描述**：暗色 `border #565049` 对背景约 2.15:1、`borderSecondary #4A4540` 约 1.80:1，低于 3:1，边框几乎不可见。
- **预期结果**：提亮至约 `#6B6259`/`#756B60`，边框对背景 ≥3:1，卡片/表格/输入框边界清晰。

### D4｜亮色 textTertiary 对比度低于 WCAG AA 【高】
- **描述**：亮色 `textTertiary #817A70` 对背景约 4.05:1，低于 AA 4.5:1。
- **预期结果**：调深至约 `#756D63`，三级文本达 AA ≥4.5:1。

### D5｜暗色模式表格 hover 背景完全不可见 【中】
- **描述**：`--color-bg-section` = `rgba(accentRgb, 0.025)`（2.5% 透明度），暗色表格 hover 背景不可见。
- **预期结果**：暗色不透明度提升至 0.08–0.12，表格 hover 有可感知的高亮反馈。

### D6｜暗色模式选中文字颜色无视觉区分 【低】
- **描述**：`globals.css` L76 暗色 `::selection` 文字设为 `var(--color-text)`，与正文同色，选中无区分。
- **预期结果**：改为 `var(--accent-text)`（或高对比强调色），文本选中状态清晰可辨。

## E. CSS 变量缺失与硬编码颜色清理

### E1｜WorkspaceCreationPage.css 引用未定义 CSS 变量 【中】
- **描述**：`WorkspaceCreationPage.css` L61/L169 引用未定义的 `--accent-bg`、`--accent-border`，强调样式失效。
- **预期结果**：在 `tokens.ts` 补定义这两个变量（亮/暗两套），或改用已有 accent 变量；强调样式在两种主题下均生效。

### E2｜chat.css app-header 暗色背景色温不一致 【低】
- **描述**：`chat.css` L53 app-header 暗色背景 `rgba(17,25,40,0.4)` 偏冷蓝，与暖色暗主题（背景 `#161513`）色温冲突。
- **预期结果**：改用暖色调 CSS 变量，app-header 与整体暗色主题色温统一。

### E3｜cmdk-overlay 遮罩层硬编码 rgba 【低】
- **描述**：`chat.css` L626 遮罩用硬编码 `rgba(0,0,0,0.50)`。
- **预期结果**：新增 `--color-overlay` 变量并引用，遮罩透明度在主题层统一管理。

### E4｜ErrorBoundary.tsx 硬编码 color: '#fff' 【中】
- **描述**：`ErrorBoundary.tsx` L59 硬编码 `color:'#fff'`，在暖色暗色 accent 背景上对比不当。
- **预期结果**：改为 `var(--color-text-on-accent)`，所有主题下错误界面文字对比度达标。

### E5｜WorkspaceCreationPage.css 硬编码 box-shadow 【低】
- **描述**：`WorkspaceCreationPage.css` L62 硬编码 `box-shadow: rgba(55,42,30,.06)`，暗色下不可见。
- **预期结果**：替换为 `var(--shadow-md)`，阴影在亮/暗模式均正确呈现。

## F. 代码高亮（暗色）

### F1｜highlight.js 仅导入亮色主题 【中】
- **描述**：`globals.css` L7 仅导入亮色 `highlight.js/styles/github.css`，暗色下代码高亮不可见。
- **预期结果**：导入暗色主题或迁移到 CSS 变量，暗色模式代码块语法高亮清晰可读。

### F2｜hljs token 颜色硬编码未用 CSS 变量 【低】
- **描述**：`globals.css` L269-276 暗色 hljs token 颜色硬编码为 6 个十六进制值。
- **预期结果**：在 `tokens.ts` 统一定义这些 token 颜色变量，代码高亮配色由主题统一管理、便于维护。

## G. CSS 卫生（优先级/重复清理）

### G1｜globals.css 中 !important 过多 【低】
- **描述**：`globals.css` L328-356 有 15+ 处 `!important`，其中 L343 表格 hover 背景被 `!important` 锁死且暗色不可见。
- **预期结果**：用更高优先级选择器替代 `!important`，表格 hover 等在暗色下正常生效；`!important` 数量显著下降。

### G2｜globals.css 暗色覆盖代码块重复 【低】
- **描述**：`globals.css` 暗色覆盖存在完全重复块（L364-407 与 L408-450 逐行一致）。
- **预期结果**：删除重复块，样式表无冗余、单一来源，行为不变。

## 优先级建议（清单末尾的 2 条 · 与上文条目对应）

### 建议一：优先修复"注册后 403 跳转 + 三态路由守卫"（对应 A1/A2/A3）
- 依据：注册成功后直接跳转到需空间权限的页面是**新用户流失首因**。
- 下一步：在 `ProtectedRoute` 区分三态；注册成功后引导到空间加入/搜索首页；完善 403 引导页。

### 建议二：优先修复"暗色模式 WCAG 对比度 + CSS 变量缺失"（对应 D2/D3/D4/D5、E1、F1/F2 等）
- 依据：多处文本/边框对比度低于 WCAG，未定义变量导致样式失效，直接影响可访问性与观感。
- 下一步：在 `tokens.ts` 将暗色文本/边框调至 WCAG 合规，补定义 `--accent-bg`/`--accent-border`，代码高亮暗色化。

## 安全交付要求（前端风险可接受，但仍保持谨慎）

1. **开工前创建备份分支**（如 `backup/ui-ux-<日期>`）。
2. **逐组小步提交**（A→G 分组），每组可独立验证与回退；避免跨组混提交。
3. **颜色/令牌类改动优先集中在 `tokens.ts`**，单点修改、全局生效，降低散点硬编码风险。
4. **每次前端改动**：`git add` → `docker compose build frontend` → 重建后验证；跑 `lint`/`typecheck`/`test`/`check:i18n`/`build`。
5. 涉及颜色的条目须做**对比度自测**（AA：正文 ≥4.5:1，边框/图形 ≥3:1），并同时检查亮/暗两种模式。
6. 每项以本计划的**预期结果**为验收标准；实现中若发现与描述不符（如 B5 注册表单已 onBlur），以代码实际为准并记录。

## 建议实施顺序（价值/风险优先）

A（1-3 新用户流失链，高价值）→ D（对比度合规，改 tokens 单点低风险）→ E（变量缺失/硬编码，低风险）→ F（代码高亮）→ B（反馈/防误操作，中等改动）→ C（响应式/动画）→ G（CSS 卫生收尾）
