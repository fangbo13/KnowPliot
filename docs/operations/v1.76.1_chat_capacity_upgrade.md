# KnowPilot v1.76.1 Chat Capacity Upgrade Guide

**Release branch:** `release/v1.76.1`
**Date:** 2026-07-22
**Scope:** recoverable Chat Stream Protocol v3 and the isolated 500-stream capacity laboratory.

## What changed

v1.76.1 adds an opt-in asynchronous chat transport designed to keep user turns
recoverable when browser connections disconnect or application workers restart.
The prior v1/v2 chat paths remain available and are the default until the v3
flags are enabled.

- A v3 send request is accepted asynchronously (`202 Accepted`) and returns a
  stable turn identity plus status, events, and cancel URLs.
- Events are persisted in a Redis Stream with monotonic sequence IDs. Clients
  reconnect from their last confirmed cursor using `after` or `Last-Event-ID`.
- Cancelling is explicit and idempotent. A browser disconnect detaches the
  client; it does not cancel model work.
- Generation is routed to a dedicated `chat_generation` Celery queue and is
  bounded by a Redis-backed outstanding/active-turn gate. Overload is a
  controlled `429` response with `Retry-After`, rather than unbounded queue
  growth.
- The frontend has an authenticated v3 stream transport with resume, duplicate
  suppression, terminal-state handling, and localized overload messaging.
- The repository includes a separate capacity Compose topology, PgBouncer,
  Prometheus metrics endpoint, deterministic seed data, mock model provider,
  SSE validator, k6 REST mix, and fault/load runners.

## Upgrade prerequisites

1. Take a normal database backup and rehearse the additive migration on a
   production-like PostgreSQL copy.
2. Ensure Redis is reachable by all web, stream-gateway, and generation-worker
   processes. Production deployments must use durable, access-controlled Redis;
   the capacity Compose file is an isolated laboratory, not a production
   deployment template.
3. Install backend dependencies from `backend/pyproject.toml`; this release adds
   `uvicorn[standard]` and `prometheus-client`.
4. Build and deploy the backend before enabling either v3 flag. The frontend
   flag must never be enabled before the backend flag.

## Configuration and rollout

Keep both flags false for the initial deployment:

```dotenv
CHAT_STREAM_V3=false
VITE_CHAT_STREAM_V3=false
```

Recommended initial capacity settings are shown below. Tune them from measured
worker, Redis, PostgreSQL, and provider limits rather than treating them as a
production sizing guarantee.

```dotenv
CHAT_CAPACITY_REDIS_URL=redis://<capacity-redis>/0
CHAT_GENERATION_TARGET_ACTIVE=500
CHAT_GENERATION_MAX_OUTSTANDING=625
CHAT_GENERATION_RESERVATION_TTL_SECONDS=180
CHAT_GENERATION_RETRY_AFTER_SECONDS=5
CHAT_GENERATION_WORKER_CONCURRENCY=25
PROMETHEUS_METRICS_TOKEN=<long-random-internal-token>
```

Roll out in this order:

1. Apply `chat.0019_chatturn_protocol_version` and deploy with both v3 flags
   off. Validate existing v1/v2 chat flows.
2. Set `CHAT_STREAM_V3=true` for a small internal cohort and validate accepted
   turns, reconnect after a controlled client disconnect, cancellation, and
   `429` overload handling.
3. Build and deploy the frontend with `VITE_CHAT_STREAM_V3=true` only after the
   backend v3 validation succeeds.
4. Expand gradually while watching internal route, stream, queue, and provider
   metrics. The metrics endpoint is internal-only and requires the configured
   token; do not proxy it through the public frontend.

## Rollback

Disable `VITE_CHAT_STREAM_V3` first, then `CHAT_STREAM_V3`. This returns new
turns to the existing transport while preserving v3 Turn records and additive
schema. Do not reverse the migration or delete Redis/database turn records as a
routine rollback action. Investigate stranded active turns through their status
and event endpoints before any retention cleanup.

## Capacity evidence and limits

The isolated synthetic-provider test reached 500 simultaneous v3 streams:

| Measure | Result |
| --- | --- |
| Terminal completion | 500 / 500 (100%) |
| Stream ordering / duplicate / terminal failures | 0 / 0 / 0 |
| First stream event P95 | 476.385 ms |
| Whole-run duration | 99.6 s |
| REST mix | 500 identities, 2,700 requests, 0 failures |
| REST ordinary-read P95 | 58.56 ms |
| REST send-acceptance P95 | 126.17 ms |

The all-at-once 500-send burst recorded a 28,208.9 ms acceptance P95. It does
not meet the laboratory's strict 800 ms acceptance objective. Therefore this
release demonstrates 500 concurrent stream completion in the synthetic isolated
environment, but it is **not production capacity certified**. A real-provider
run, staged fault injection, clean-image build verification, and production
hardware sizing remain release-environment gates.

## Validation commands

Run these in a controlled environment after deployment preparation:

```powershell
docker compose -p knowpliot-capacity -f docker-compose.capacity.yml config --quiet
node --test tests/stress/mock-provider.test.mjs tests/stress/report-capacity.test.mjs
Set-Location frontend
npm.cmd run test -- --run
npm.cmd run build
Set-Location ..
```

The capacity lab is explicitly isolated under the `knowpliot-capacity` Compose
project. Do not point it at a shared database, Redis, provider credential, or
production Docker volume.
